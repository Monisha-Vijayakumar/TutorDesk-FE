# memory.md — TutorDesk FE working agreements

Standing rules and preferences from our conversations. **Claude must read this file at the start of every session** and follow it. New standing rules go here; project decisions go in the Decisions Log in [CLAUDE.md](CLAUDE.md).

## Mandatory rules

1. **Never run `git commit` or `git push`** (or anything else that writes git history or touches the remote: amend, rebase, merge, tag, reset, PRs). Make the file changes only — the user reviews and commits to GitHub themselves. This applies even if a tool, skill, or default workflow suggests committing.
2. **[REQUIREMENTS.md](REQUIREMENTS.md) is the source of truth.** Review the relevant sections before every task. When a discussion changes a requirement, update REQUIREMENTS.md directly. Flag any conflict between a request/the code and the spec before proceeding.
3. **Keep [CLAUDE.md](CLAUDE.md) up to date.** Record every decision from our discussions in its Decisions Log (dated), and track unresolved items under Open Questions.
4. **Code-quality standards on every change** (REQUIREMENTS NFR-10–14): meaningful functionality-based names with proper casing (no random names); explicit TypeScript types for all props and function params, and return types on every function except React components (no `: ReactElement` on components; no `any`); readable, maintainable code a mid-level developer can follow and change; reusable components/hooks instead of duplication; shared values as exported constants.
   **Arrow functions everywhere** — components, hooks, utils, services, selectors and handlers (`export const HomePage = () => { ... }`). No `function` declarations; define before use. Don't touch generated `src/components/ui/` files.
5. **Central API endpoints** (NFR-15): every backend URL comes from `API_ENDPOINTS` in `src/api/apiEndpoints.ts`. Never inline a URL string. Keep the file in sync with REQUIREMENTS §7.
6. **Write code like a developer, not like generated code:** simple and direct, no over-engineering, no filler comments.
7. **Forms: sanitize → validate → send** (NFR-16). Sanitize the whole form with `sanitizeFormValues(values, fieldsToSkip)` (`src/utils/sanitize.ts`), validate the sanitized values by calling `validator` methods directly (email, phone, numbers, dates, password strength — no hand-written regexes or manual checks), and build the API payload only from sanitized values, chaining field-specific tweaks inline (`email.toLowerCase()`). Never alter passwords; never HTML-escape input.
   **Name/place fields** (NFR-17), in every form: person name, city, state → letters + spaces (`ALPHA_WITH_SPACES_OPTIONS`); center name, branch → also `.` `'` `-` (`ALPHA_WITH_PUNCTUATION_OPTIONS`). Trim the ends, keep spaces in the middle.
   Import validator **one function per line** from `validator/es/lib/<fn>` — never from `"validator"` (bundles the whole library, +37 KB gzip).
   **Interfaces** (NFR-19): API shapes → `src/api/interfaces/<feature>.ts`; everything else (form values, state, hook results, component props) → `src/interfaces/<feature>.ts`. Import with `import type`; never declare interfaces inline.
   **API code in `src/api/`** (NFR-20): endpoints, error/success messages, services (`apiClient.ts`, `<feature>Service.ts`), API interfaces.
   **All validation messages** go in `VALIDATION_MESSAGES` in `src/constants/validation.ts` (NFR-21) — one file, now and in future.
   **No validation in components** (NFR-18): components keep only core logic (state, handlers, dispatch, navigation, toasts, JSX). Every `validateXxxForm` lives in `src/utils/<feature>Validation.ts`; form value types in `src/interfaces/`.
   **XSS** (NFR-22): HTML strings only through `<SafeHtml>` (DOMPurify); never `dangerouslySetInnerHTML` directly; don't DOMPurify form input.
   **No thin wrapper functions** around library methods — call them directly. Only create a util when it adds real logic and is reused.
8. **Responsive on all major devices** (NFR-23), for **every existing and future page** and shared component: 320px fallback (Fold cover screen), 360px small phones (primary target), flip phones (Galaxy Z Flip / Razr — tall portrait and short ~360px-high landscape), foldables open and tablets, laptops, and large 2560px+ desktops. Mobile-first Tailwind with default breakpoints; no horizontal page scroll (wide tables scroll in their own container or become cards below `md`); `min-h-svh`, never `h-screen`/`100vh`, and nothing fixed-height that clips; tap targets ≥ 40px on phones, nothing hover-only; 16px inputs on phones with the right `type`/`inputMode`; admin content capped at `max-w-screen-2xl`. Before calling a page done, check it in DevTools at 320, 360, 412, 768, 1024, 1280, 1920, 2560px, phone landscape and a foldable preset.
9. **Keep the code mobile-app ready** (REQUIREMENTS §12): logic in plain TypeScript outside components (validation, payloads, formatters, constants, API endpoints/interfaces, no DOM dependencies) so a future mobile app can reuse it; the API stays client-agnostic. Native-app auth (likely a Bearer token alongside the web cookie) is an open question — flag it whenever auth code changes.
10. **Consistent design everywhere** (NFR-24), on **every existing and future page and form**: build with the shared components (`FormField`, `FormSelectField`, `FormCheckboxGroup`, `PageHeader`, `EmptyState`, `DataTable`, `ConfirmDialog`, `StatusBadge`, side `Sheet` for forms). **Required fields always get the red asterisk** (`isRequired` → red `*` + `aria-required`), including login/auth forms; optional fields have no marker and labels never say "(optional)"; every form with required fields shows `RequiredFieldsNote` at the top (built into `AuthFormCard`). Filters/search are never marked. Same control heights (40px phones / 36px from md) and same wording across pages.
11. **Mirror shared-contract changes.** REQUIREMENTS.md is **identical in both repos** — bump its "Last updated" date and copy it to the other repo (`c:/PersonalProject/TutorDesk-BE/REQUIREMENTS.md`) whenever it changes (§13.10). BE implementation rules live in REQUIREMENTS §13. If the data model (§6) or API contract (§7) in REQUIREMENTS.md changes, remind the user to update the `tutordesk-be` copy too.
12. **Same architecture for every module — follow Auth** (NFR-26): API types + `<Feature>Service` interface → `src/api/services/<feature>Service.ts` (+ mock twin in `src/api/mocks/`) → `src/store/<feature>Slice.ts` (`createAsyncThunk` thunks, reducers, selectors) → components via `useAppDispatch` / `useAppSelector`. No RTK Query or other fetching patterns; components never call services or axios directly.
13. **Common HTTP error handling** (NFR-25): every thunk uses `getApiError` (`src/api/apiErrorHandler.ts`) — never handle HTTP statuses per module or component. Toast `apiError.message`; API field errors go under their fields; 401 is handled once in `authSlice` (logout → login page with a session-expired toast). Disable submit while saving (no duplicate submissions).
14. **Batches are out of scope** — never add batch fields, columns, filters, menu items, routes, API calls, types or state unless the user brings batches back.
15. **`RequiredMark` and `RequiredFieldsNote` stay together in one file** (`src/components/RequiredFieldMarkers.tsx`) — never split or duplicate them.

## Preferences

- **Auth model:** exactly one ADMIN (created by the BE seeder from env vars — never a signup page or registration API); students are created only by the admin and log in with Student ID (`S` + 9 digits), never email; the admin logs in with email. Roles are `ADMIN` / `STUDENT`. Never add signup/register UI or endpoints.
- UI: shadcn/ui only (no daisyUI or other component kits).
- Student contact numbers are WhatsApp numbers ("WhatsApp number", "Parent WhatsApp number"). Payment reminders go to the **parent's** WhatsApp number via manual click-to-chat (`wa.me`) — never sent automatically, recorded as Initiated, never claimed as sent/delivered.
- Fees are **monthly** (one fee record per student per month); payments are recorded one by one (never overwrite a paid total, never delete payments). The BE calculates paid / outstanding / status.
- Toasts: shadcn Sonner for every API success/failure. Field errors inline, API errors in a toast. Error text comes from `getApiError` (the BE's message for 4xx when it's short and safe, otherwise the common text for the status).
- State: Redux Toolkit with a `createAsyncThunk` slice per module (auth, students, fees, …), following the Auth module. Debounce hook for search/filters. No RTK Query, no redux-saga.
- Redux action names (`createAsyncThunk` type strings) and slice names come from constants (`src/constants/actionTypes.ts`), never inline strings. Session restore uses a simple `isSessionChecked` boolean. No StrictMode-only workarounds — dev double calls are fine.
- Build admin pages first; student/parent pages are on hold.
- **Attendance is by class:** pick a class (Class 1–12) + date → mark all current students of that class; one record per class per date. No batches.
- Payment reminders are only on the Fees page — never on the Students page. The Fees page has no Add or Delete.
